# Скоринг сообществ: от «нашли чат» до «идём туда сегодня»

Каталог без скоринга бесполезен: 300 чатов — это не список задач, а список отвлечений.
Мы держим **два независимых рейтинга** из одних и тех же признаков, потому что чат, где удобно брать заказы,
и чат, где удобно продавать пилот, — это почти всегда разные чаты.

## 1. Признаки (считаются отдельно, не смешиваются в одно число)

| Признак | Что измеряет | Откуда берём сигнал |
|---|---|---|
| `topical_fit` | Насколько тема чата совпадает с нашим предложением | Эмбеддинги описания + 200 последних публичных сообщений; ручная категория |
| `commercial_relevance` | Есть ли в чате деньги и ЛПР | Наличие оферов/прайсов/вакансий; присутствие в рекламных базах (Telega, Collaborator, TgMaps) |
| `openness` | Можно ли туда зайти и писать | Публичный/по инвайту; открыт ли постинг; есть ли премодерация |
| `consent_likelihood` | Насколько уместен наш заход по правилам чата | Закреп и правила: разрешён ли промо-день/тред; банят ли за оффер |
| `safety` | Репутационный и правовой риск | Серые тематики, скам, накрутка → `block` |
| `freshness` | Живой ли чат сейчас | Дата последнего сообщения; сообщений за 7 дней |
| `activity` | Хватит ли потока, чтобы поймать сигнал | Сообщений/день, уникальных авторов/день, доля ответов |
| `duplication_risk` | Не то же ли это сообщество под другим именем | Пересечение админов, кросс-репосты, схожесть описаний, общий домен инвайтов |

Правила:
- `safety = block` или `freshness = dead` → чат выбывает независимо от остальных признаков.
- `duplication_risk` не понижает балл, а **склеивает** записи: у кластера один владелец и одна история касаний.
- Число участников само по себе — **не** признак качества. 40k мёртвых участников хуже 900 живых.

## 2. Два рейтинга

**ORDER_SCORE** (идём брать заказы) =
`0.30·demand_signal + 0.25·activity + 0.20·consent_likelihood + 0.15·topical_fit + 0.10·freshness`

где `demand_signal` — частота сообщений вида «ищу подрядчика / нужен разработчик / есть задача» за 30 дней.
Это главный признак: чат с двумя заказами в день ценнее чата с 30 000 участников и нулём запросов.

**PILOT_SCORE** (идём продавать пилот ReachFlow) =
`0.30·icp_density + 0.25·pain_signal + 0.20·commercial_relevance + 0.15·consent_likelihood + 0.10·activity`

где `icp_density` — доля ЛПР (владельцы агентств, фаундеры, РОПы) среди активных авторов,
`pain_signal` — частота жалоб на лидген: «дорогая заявка», «где брать клиентов», «слил бюджет», «нет входящих».

## 3. Как считать `demand_signal` и `pain_signal` без парсинга людей

Берём только публичный контент чата (t.me/s/… или MTProto-история), считаем **сообщения**, а не авторов:

```
demand_signal = matches(DEMAND_PATTERNS, messages_30d) / days
pain_signal   = matches(PAIN_PATTERNS,   messages_30d) / days
```

`DEMAND_PATTERNS`: ищу подрядчика|нужен разработчик|ищу команду|есть задача|нужна интеграция|ищу бота|кто возьмётся|бюджет ~
`PAIN_PATTERNS`: дорогой лид|стоимость заявки|где брать клиентов|нет заявок|слил бюджет|не окупается|холодные продажи|нужен трафик

Мы храним ссылку на сообщение-повод (evidence), а не профиль автора — см. `compliance.md`.

## 4. Что делать с результатом

| Полоса | ORDER_SCORE | Действие |
|---|---|---|
| A | ≥ 0.70 | Вступаем, включаем алерты по DEMAND_PATTERNS, дежурим в рабочие часы |
| B | 0.45–0.69 | Вступаем, читаем дайджестом раз в день |
| C | < 0.45 | Держим в резерве, перепроверяем раз в месяц |

| Полоса | PILOT_SCORE | Действие |
|---|---|---|
| A | ≥ 0.70 | Контент-присутствие + точечные ответы на pain-сообщения |
| B | 0.45–0.69 | Наблюдаем, заходим при явном сигнале |
| C | < 0.45 | Не тратим время |
